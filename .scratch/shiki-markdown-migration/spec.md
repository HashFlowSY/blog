## 新实现约定

### 内容目录和编译接口

`src/lib/markdown/` 提供一个构建时编译入口 `compileMarkdownDocuments(sources, { basePath })`。内容目录先读取 YAML 并完成内容契约校验，再把已发布的文章和项目正文一次交给该入口。每项输入带文件路径、正文起始行、标题和正文。编译器每篇解析一次，返回以文件路径为键的只读结果，每项包含不可变的 `{ tree, outline, searchBlocks, readingStats }`。无法发布的输入以带源位置的错误中止整次构建。详情从 `document` 读取正文树和目录，文章详情同时读取字词数和估时。搜索路由读取已发布文章的 `searchBlocks`。正文树留在服务端，归档卡片只接收预计分钟数和卡片字段。首页、RSS 和 sitemap 消费各自需要的元信息。

1. **读入 YAML 和正文**。使用 `vfile-matter` 5.0.1，明确采用 YAML 1.2 Core 且拒绝重复键。UTF-8 读取并处理 BOM；只接受文首成对的 `---`，记录正文起始行，错误定位支持 LF、CRLF。识别 `vfile-matter` 在找不到封套时不剥离输入的行为，由目录报出缺失或未闭合封套；`---js` 和无效 YAML 均拒绝。未加引号的 ISO 日期按字符串交给 Zod，仍校验真实日期和 `updated ≥ date`；frontmatter 必须是映射，布尔状态必须是 YAML 布尔值。发现仍限两个目录的直属 `.md`。汇总两集合的解析与契约错误；校验草稿提供的字段后，从正文编译和所有发布产物中排除。保留生产快照的复用和开发环境新增、修改、删除内容后重建。 [YAML 解析器源码](https://github.com/vfile/vfile-matter/blob/5.0.1/lib/index.js#L32-L75) · [内容契约](../../src/lib/content-contracts.ts) · [内容目录](../../src/lib/content-catalog.ts#L338)
2. **解析和净化**。启用 CommonMark 与 GFM。仅当第一顶层节点是与页面标题语义相同的 H1 时移除它，再生成标题 ID。比较已解码、折叠空白的可读文本，支持强调、链接、图片替代文字和行内代码；不同的 H1 保留，移除的标题不占 slug。自定义的类型化 `code` handler 从 `mdast.code.value` 记录原文、语言、行范围和位置，随 `<pre>` 的内部 `data` 通过净化。保留默认的原始 HTML 丢弃策略和协议校验，移除非法图片，净化前的节点属性只允许正文语义所需内容，包括有序列表起始值、任务项禁用和选中状态、图片替代文字与题注属性、脚注无障碍属性及表格对齐。Shiki 的受控主题样式在净化后生成。 [默认代码 handler](https://github.com/syntax-tree/mdast-util-to-hast/blob/13.2.1/lib/handlers/code.js) · [净化顺序](https://github.com/rehypejs/rehype-sanitize#example-syntax-highlighting) · [净化时保留内部数据](https://github.com/syntax-tree/hast-util-sanitize/blob/5.0.2/lib/index.js#L725-L735)
3. **确定最终链接**。正文 H1–H6 采用每篇独立的 GitHub slugger，统一由净化器加 `user-content-`。保留两篇文章和项目案例已有的 17 个公开片段（更新项目说明时保留这些小节标题），见[基线清单](coverage-audit.md#已发布锚点基线)。Markdown 同页标题链接写 `#标题-slug`，解码一次后查找最终 ID；未知或无效片段报文件和行号。把已发布文章里带前缀的作者链接一次性改为 `#使用前的检查清单`。Markdown 的站内根路径由编译器统一应用一次 `BASE_PATH`，保留查询参数和片段；跨页片段使用目标页公开的 ID。相对路径仍按浏览器中的发布 URL 解析。普通外链、协议相对 URL 和邮件链接沿用净化器许可的语义；不把它们当作站内根路径重写。不要给作者已有部署前缀写剥除或二次改写的兼容分支。用真实本地图验证两种部署前缀下的请求。 [现有 slug 算法](https://github.com/rehypejs/rehype-slug/blob/6.0.0/lib/index.js#L27-L44) · [站点路径工具](../../src/lib/site.ts#L95)
4. **从语义树提取目录、搜索和阅读统计**。目录只取正文 H1–H3 的标题文本和最终 ID，重复中文标题和内联格式按实际显示结果处理。搜索先于高亮和控件提取。段落、标题、列表项、表格行和代码块各自成块，表格单元格以空格分隔，代码用原文，脚注引用数字、回链标签和隐藏标题不进入索引。保留文章搜索的 `slug` / `blocks` 接口、主题筛选及排名。同一提取阶段从净化后的正文树统计阅读数据，使用下文单独定义的正文范围。

脚注在转换前把同一标识的定义和引用映射到同一个序号，按每篇文档分配。使用独立的 `footnote:` 命名空间，让引用 ID 由脚注序号和出现次数决定。脚注标签 ID 和 `aria-describedby` 也归入这一命名空间。净化器统一加 `user-content-`，之后给生成的脚注 `href` 绑定最终目标并验证正向、回链及 ARIA 引用都唯一可达。脚注标签和回链使用中文，脚注区不进入目录，同一脚注的每处引用都能回到各自位置，按引用顺序编号，未引用的定义不显示。定义正文进入搜索和阅读统计，控件与生成的标签排除。 [上游引用生成](https://github.com/syntax-tree/mdast-util-to-hast/blob/13.2.1/lib/handlers/footnote-reference.js#L18-L55) · [脚注转换选项](https://github.com/remarkjs/remark-rehype#example-footnotes-in-languages-other-than-english)

### 搜索、归档与推荐

- 搜索索引沿用 `{ slug, blocks }` 数组，每个已发布文章 slug 恰有一条；项目和草稿不进入。编译器输出正文片段时，保留表格行内各单元格的分隔、嵌套列表顺序及已显示脚注正文。代码块从作者的代码文本取词并折叠空白。索引内没有 frontmatter、生成控件或 Shiki token。
- 保留归档现有交互：纯主题筛选不请求索引，首次关键词请求后复用索引。中文输入法上屏后才更新关键词。查询按字面、忽略大小写，先标题，再摘要或标签，再正文；同组按日期和 slug 排序。正文命中保持原文及 `mark` 高亮，裁剪不切断 Unicode 码点。索引不可用或与目录不一致时，显示错误和重试入口；不显示部分搜索结果。没有文章、无匹配、取消单个主题和清空筛选是独立状态。返回正文仅命中的文章卡片时，要等索引和卡片到位才恢复焦点。 [归档交互](../../src/components/post/post-archive.tsx#L42) · [搜索规则](../../src/lib/post-search.ts#L23) · [返回焦点验收](../../e2e/post-detail.spec.ts#L53)

### 正文字词数与预计阅读时长

1. **来源。** 统计净化后、Shiki 加入高亮标记前的正文。计入显示的标题、段落、列表、引用、表格、脚注定义正文、链接文字和行内代码；排除块级代码、被移除的重复首标题、脚注引用序号及回链、脚注区的生成标签、frontmatter、链接和图片的属性及页面控件。块级代码仍按原文进入搜索。每个符合条件的文本节点只计一次，在段落、列表项、表格单元格和换行处保留词边界；被粗体或链接拆开的连续文本按显示内容合并。
2. **算法。** 将正文文本按 NFC 规范化。用 Unicode 的脚本和类别属性逐码点统计汉字、假名、韩文和注音的字母及字母数字（`Letter` / `Letter_Number`）；标点不计。每个已计的字符在其余文本中留下词边界。用 `Intl.Segmenter("zh-CN", { granularity: "word" })` 统计其余 `isWordLike` 片段，数字片段也按词计。返回 `{ cjkCharacters, otherWords, minutes }`，其中 `minutes = ceil(cjkCharacters / 500 + otherWords / 200)`。500 和 200 是本站估算参数。例如 500 个 CJK 字和 200 个其他词估为 2 分钟。没有可计正文时返回三个 0。 [ECMA-402 词分段定义](https://tc39.es/ecma402/#sec-createsegmentdataobject)
3. **展示。** 新建 `src/components/post/article-reading-meta.tsx`，接收统计结果与展示场景。文章详情显示“正文 500 字 · 200 词 · 约 2 分钟”，归档和关联文章卡片显示“约 2 分钟”。详情省略值为 0 的单位；没有可计正文时整项省略。详情在服务端渲染，归档在现有客户端筛选组件内复用同一展示组件。分词与估算只在服务端内容编译时执行。项目详情仍无字词数和估时；滚动阅读进度和归档篇数由各自的界面处理。 [归档组件边界](../../src/components/post/post-archive.tsx#L1)

验收样例：用 `## 示例` 作标题，正文写 `使用 **Shiki** 阅读[说明](/posts/example/)，查看`，接上行内代码 `codeToHast` 和脚注引用；加入一个 TypeScript 围栏，内有重复 201 次 `token` 的注释，再定义 `[^tip]: 保留空行。`。用这份源文调用现有估算器得到 2 分钟；取可计正文在 Node.js 24.22.2 核对字词规则后，新详情预期“正文 14 字 · 2 词 · 约 1 分钟”，归档卡片预期“约 1 分钟”。改变链接目标或扩展围栏代码不改变新统计。实际编译和渲染留给迁移验收。

### Shiki 的代码约定

- **固定一条高亮路径**。仅在文档集合包含代码块时初始化服务端 Shiki。根据同一次 Markdown 解析收集并去重实际用到的语言，连同 Markdown 围栏等场景内嵌的可识别语法一起加载。每个代码块用同一个实例的 `codeToHast` 产生 `<pre><code>`。取返回树里的 `<pre>` 替换原节点，标签和复制原文经服务端节点数据传给新代码框。主题采用已预览的 `github-dark-high-contrast`，指定行用本站黄色标记。行内代码按正文排版显示。 [Shiki 实例复用](https://shiki.style/guide/best-performance) · [内嵌语法探测](https://github.com/shikijs/shiki/blob/v4.6.0/packages/core/src/utils/strings.ts#L74-L129) · [代码输出](https://github.com/shikijs/shiki/blob/v4.6.0/packages/core/src/highlight/code-to-hast.ts)
- **语言是作者输入契约**。接受 Shiki 打包语言的官方 ID、官方别名，以及 Shiki 原生的 `text`、`plaintext`、`txt`、`plain`。`ansi` 终端转义渲染不在本次输入契约内。省略语言的围栏和缩进代码按 CommonMark 的纯文本代码块定义，统一使用 Shiki `text`。带语言的代码框显示作者标签，使用 Shiki 解析该标签；无语言及缩进代码统一显示“纯文本”并可以复制。显式未知语言直接报错，指出文件、行号和标签。README 列出可用语言写法和此项行为变化。 [CommonMark 围栏](https://spec.commonmark.org/0.31.2/#fenced-code-blocks) · [Shiki 支持的语言](https://shiki.style/languages) · [纯文本类型](https://github.com/shikijs/shiki/blob/v4.6.0/packages/types/src/langs.ts#L4-L6)
- **行号以围栏代码为准**。支持 `{1,3-5}` 这一种行高亮语法，允许列表分隔处的空格。校验整个表达式和每个整数，范围必须在代码实际行数内且起点不大于终点。空代码没有可标记行。非法、越界和超大范围直接使构建失败。先校验再按实际行数分配，用 Shiki `line` 钩子设置 `.highlighted`，无需重切 token。用于高亮的换行统一为 LF，复制仍使用未经 trim 的 `mdast.code.value`。 [官方区间解析源码](https://github.com/shikijs/shiki/blob/v4.6.0/packages/transformers/src/transformers/meta-highlight.ts) · [逐行钩子](https://github.com/shikijs/shiki/blob/v4.6.0/packages/core/src/highlight/code-to-hast.ts#L186-L215)
