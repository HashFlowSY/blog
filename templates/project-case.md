# Project Case 作者模板

> 此文件仅用于作者撰写，位于公开内容加载目录之外。复制到 `content/projects/zh-CN/` 前，请以可核实的事实补全 frontmatter 和正文；在所有公开证据准备完成前，保持 `draft: true`。

## 发布前 frontmatter

将下列占位符替换为当前项目的真实信息。发布时需要显式设置 `draft: false`；不要添加 `template` 字段。

```yaml
title: "<项目名称>"
slug: "<稳定的小写-kebab-case-slug>"
date: "<YYYY-MM-DD>"
tags:
  - "<标签>"
description: "<用一句话说明项目解决的问题和交付物>"
cover: "/assets/<已确认存在的封面文件>"
source: "<可选：HTTPS 源代码地址>"
demo: "<可选：HTTPS 演示地址>"
role: "<本人实际负责的工作>"
duration: "<实际参与或交付周期>"
result: "<有证据支持的实际结果>"
featured: false
draft: false
```

## 问题背景

- 说明谁在什么情境下遇到了什么问题，以及现有流程或系统的具体限制。
- 区分已观察到的事实、尚待验证的假设和不应公开的敏感信息。
- 只写有来源或本人直接参与过的背景，不代入客户名称、规模或影响范围。

## 我的角色

- 明确本人负责的决策、实现、协作或验证环节。
- 说明边界：哪些部分由他人、外部系统或既有团队负责。
- 写出可以追溯到本人工作的具体产出，而非泛化的团队成果。

## 约束与风险

- 记录时间、技术、数据、权限、合规、兼容性或协作上的实际限制。
- 写清哪些高风险动作需要确认、审计、回退或降级方案。

## 方案

- 用项目实际采用的结构描述关键流程、组件或接口。
- 说明输入、输出、失败状态和可观测性如何处理。
- 链接到可公开的代码、文档、截图或演示；敏感材料应脱敏或不公开。

## 关键决策

对每项关键取舍记录：

1. 当时需要解决的具体问题；
2. 考虑过的可行选项；
3. 选择的依据与代价；
4. 该决策如何被后续验证或调整。

## 验证方法

- 说明验证对象、方法、通过条件和失败时的处理方式。
- 可包含测试记录、评测样例、运行日志、用户反馈或发布检查清单。
- 不把尚未执行的计划写成已经完成的验证。

## 结果证据

- 仅陈述可以由链接、记录、截图、版本历史或明确观察支持的结果。
- 对指标写明口径、时间范围和来源；没有可靠证据时，说明限制或暂不公开。
- 不使用虚构客户、周期、指标或成果填充这一部分。

## 复盘

- 记录实际有效的做法、未解决的问题和下一次会改变的决策。
- 区分项目事实与个人推断，避免将推测表述为结论。
