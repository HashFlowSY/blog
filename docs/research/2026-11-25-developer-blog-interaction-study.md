# 工程师个人博客的阅读与作品交互

2026 年 11 月 25 日。研究对象是 Hashflow 的中文个人博客。网站公开展示 Personal Blog 一个项目，以及 Codex 桌宠实践和 AI 服务术语两篇文章。第一套「纸上工作室」已经有清楚的项目入口和连续封面转场，这次把它作为保留的基线。

## 怎么看这些网站

选择公开写技术文章、发布工具或介绍本人项目的作者站。另选 Steph Ango 作以文字为主的阅读对照。沿着访客的实际任务操作：从首页辨认作者做了什么，点进一篇文章或一个项目，试一个有结果的动作，再返回。八站均在本机 Chrome 操作，桌面视口宽度为 1280 到 1440 像素。手机观察使用 390 像素视口，部分路径启用了触摸模拟。桌面 Safari 和实体手机均未覆盖。下面的数值只描述本次打开的页面和视口；未做读者测试，也未收集这些网站的转化数据。

原站的颜色、知名作者的作品数量和复杂组件都不足以证明某种设计适合 Hashflow。判断时只放入现有三条内容，再看入口是否还有意义，操作是否能带来新的信息，手机是否有同样清楚的路径。

## 中文技术写作与个人作品

### Anthony Fu · 在介绍里直接给出作品入口

桌面首页把作者正在做的工作写进自我介绍，项目名本身就是链接。Blog 归档按年组织，每条带日期、阅读时长或语言标记。从归档进入《开源的心理建设》，可以看到阅读时长、章节与英文版本。返回后，本次桌面列表仍在纵向 644px，手机仍在 1229px。Projects 的 Devframe 条目说明用途，点开另一个标签进入仓库。390px 视口中部分顶部入口变成图标，介绍段中的文字链接仍能用。[作者首页](https://antfu.me/) · [文章归档](https://antfu.me/posts) · [中文正文](https://antfu.me/posts/mental-health-oss-zh) · [项目列表](https://antfu.me/projects)

一句介绍里可以放一件具体作品，旁边接一篇真实记录。访客可以先按兴趣读，不必先弄懂站点分类。一个项目用不上生态分组。手机主导航保留中文标签，比要求读者识别图标更合适。

### idealclover · 作品的名称、用途和体验入口在一起

首页同时包含博客和作者作品。桌面和 390px 下都试了「技术」分类，点《咕咕了一年的新个人主页介绍》会在新标签打开；关闭后仍在原分类和原位置。「南哪课表」能直接进入产品。桌面可并列多个项目，手机纵向排列；本次手机首页的文章区约在 692px，个人项目区约在 1392px。作者的改版记录也解释了这个主页兼作跨平台名片的考虑。[首页](https://idealclover.top/) · [作者自述](https://idealclover.top/archives/643/) · [项目实站](https://nju.app/)

项目旁需要一句「能拿它做什么」。越靠后的项目越容易在手机首屏之外，值得在介绍里给直达入口。本站的两篇文章不需要五个分类，更没有必要借用别人的粉丝数字或徽章。

## 长文与小工具如何互相引导

### Simon Willison · 工具可以成为项目能力的直接证据

从 Weblog 的 Tools 走到作者自己的工具集合，再打开 Select Styling Specimens。样本把页面说明、浏览器实际绘制的下拉框和实现材料放在一起。桌面 1366px 和手机 390px 都在第一个控件里把 Banana 改为 Cherry，然后退回工具集合。这里核验的是原生控件值变化和返回路径。[作者博客](https://simonwillison.net/) · [工具集合](https://tools.simonwillison.net/) · [实际样本](https://tools.simonwillison.net/select-styling)

博客里已有可验证的小功能，访客可以先试一个，再看为什么这样实现。Simon 的工具数量足以支撑独立目录；Hashflow 的一个试验放在案例里就够了。

### Steph Ango · 允许读者按一个主题抵达具体文章

首页在最新文章和 Writing 目录之间给出主题入口。实际从 Tools 进入主题页，再打开 File over app，正文标题下直接给日期和阅读时长。浏览器后退回到 Tools 主题页。1366px 和 390px 都走通了同一条路径，手机主题页文档宽度为 390px。这里用它作文字阅读和主题导航的对照。[首页](https://stephango.com/) · [Tools 主题](https://stephango.com/topics/tools/) · [正文](https://stephango.com/file-over-app)

读者选主题时，结果最好立刻缩小到可读条目。现有文章只够支撑少数明确的问题，适合用「怎么做」和「怎么判断风险」这样的具体入口；几十个标签会稀释实际内容。

## 文章中的说明、控件与结果

### Josh W. Comeau · 让读者先动一个参数，再决定要不要读实现

- **首页与视觉。** 桌面首屏是浅蓝天空、彩虹、立体人物和当期课程促销。网页向下列出文章标题、摘要和阅读全文链接。顶部的 Goodies 是与写作并行的工具入口。工具页另有一套构图，背景变暗，紫色区域承载三种高度的阴影样本，参数和代码都有自己的位置。首页的促销画面是当日观察，工具与文章的连接可以独立使用。［实测］[作者首页](https://www.joshwcomeau.com/) · [阴影工具](https://www.joshwcomeau.com/shadow-palette/)
- **实际走过的路径。** 从首页点 Goodies，再点 Shadow Generator。给 Oomph 滑杆键盘焦点后按 End，读数从 0.5 变为 1，生成代码中低位阴影第一层的透明度从 0.34 变为 0.52。工具顶部的 Read the Blog Post 通向实现文章。文章先并排示范普通阴影和优化阴影，再解释多层叠加，点 Show more 还能就地展开 HSL 的补充说明。浏览器后退可回到生成器，本次 Oomph 回到 0.5。［实测］[生成器](https://www.joshwcomeau.com/shadow-palette/) · [配套原文](https://www.joshwcomeau.com/css/introducing-shadow-palette-generator/)
- **窄屏。** 390px 下，工具名称、示例区和控件沿页面向下排列。点 Tint Shadow，开关变为关闭，输出的阴影色从紫色色值变为黑色。访客能在同页读到结果；实测整个文档宽度为 390px。此处验证了开关与生成代码的联系，未读取系统剪贴板。［实测］[生成器](https://www.joshwcomeau.com/shadow-palette/)
- **对 Hashflow 的取舍。** Personal Blog 已经有全文搜索，访客可以用文章正文里真实出现的词理解「全文」的含义。例如演示搜索「倍率」，展示原文命中的一句话，保留打开整篇文章的入口。这样一个项目就足以支持一次有结果的操作，也无需用虚构的项目卡来填版面。［设计推断］[项目说明](../../content/projects/zh-CN/personal-blog.md) · [文章材料](../../content/posts/zh-CN/26-04-30.md)

### Maggie Appleton · 从一个关注点找到文章，再进到需要的段落

- **首页与视觉。** 首页用大号衬线字直接说出作者研究的对象，米白底、深灰正文和洋红色链接贯穿首屏。向下滚，长文卡片给插画、摘要和类型；笔记以标题列出。这里的“花园”对应持续积累的内容，当日花园页标出 168，读者可以按主题、成长阶段和体裁寻找入口。［实测、原站内容］[作者首页](https://maggieappleton.com/) · [The Garden](https://maggieappleton.com/garden)
- **实际走过的路径。** 从首页进入 The Garden，点 Artificial Intelligence 后，个人近况《August 2026》从可点击的结果中消失，Gas Town 笔记仍能打开，地址保持在 /garden。进入笔记，在正文点 What is Design Fiction?，旁边的文字从 Read more 变成 Show less，原处出现定义及延伸阅读链接；再点一次收起。浏览器后退回花园，本次主题选择已恢复为全部，近况重新可见。［实测］[The Garden](https://maggieappleton.com/garden) · [Gas Town 原文](https://maggieappleton.com/gastown)
- **窄屏。** 手机宽度下，花园顶部变成三个纵向排列的下拉按钮，条目排成单列。进入同篇笔记，点 Table of Contents，再选合并队列的小节，浏览器地址写入章节锚点，标题来到视口顶部，可直接把这个位置发给别人。选题会重置，章节本身有持久地址，两种状态服务不同的目的。［实测］[花园](https://maggieappleton.com/garden) · [实测章节](https://maggieappleton.com/gastown#merge-queues-and-agent-managed-conflicts)
- **对 Hashflow 的取舍。** 两篇文章可以把读者可能带来的问题直接列出来。例如「桌宠动作怎么验收」和「中转站的倍率是什么」各自指向对应原文段落。选中问题后就地出现一段有出处的摘录，想继续读的人用常规链接打开正文。168 项内容需要的多维筛选，对两篇文章而言会让读者在看到答案前多做选择。［设计推断］[桌宠原文材料](../../content/posts/zh-CN/26-05-02.md) · [术语原文材料](../../content/posts/zh-CN/26-04-30.md)

### Emil Kowalski · 先解释差异，再让读者自己点一次

从首页进入 Sonner 的制作复盘，解释通知实现的段落后就能点 Add toast。桌面连续点击第二个示例会在该演示框中看到通知叠放，旁边的示例保持独立。手机也能直接点按，再返回原来的首页列表位置。首页在 1440px 时用了约 644px 的内容列，390px 时约 342px；项目和文章都只需一个标题和一行用途说明。[个人站](https://emilkowal.ski/) · [制作复盘与可操作示例](https://emilkowal.ski/ui/building-a-toast-component) · [作品](https://sonner.emilkowal.ski/)

项目正文提到阅读时间算法时，可以让读者用一段真实文字试算；控件应出现在解释附近。整篇普通文章依然可以安静阅读，给两篇现有文章都硬加动画会削弱重点。

### Rauno Freiberg · 在点之前区分试原型、读说明和看成品

Craft 列表会写明点击后得到什么。打开 Exclusion Tabs，再点 Engineering，黑色选中层移动并调整到新标签的宽度；慢动作开关允许细看，手机也可直接点按。另一条 Invisible Details 则进入长文。1440px 下列表三列，390px 下为单列。本次桌面两次返回都到了列表顶部，手机从原型回到进入前的约 9201px。部分列表媒体只看到模糊占位，对这些媒体没有进一步作视觉推断。[Craft](https://rauno.me/craft) · [Exclusion Tabs 原型](https://rauno.me/craft/exclusion-tabs) · [Invisible Details 长文](https://rauno.me/craft/interaction-design)

一个项目也可以有「先试算」和「读实现」两种去向。区别由按钮文案提前说清楚；大量卡片、瀑布流和复杂首页并不适合当前体量。

## 从调研到本轮两个方向

| 访客的第一步               | 作者站里看见的依据                                                                         | Hashflow 的组合                                                                                                                   | 在手机上怎么试                                   |
| -------------------------- | ------------------------------------------------------------------------------------------ | --------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------ |
| 我想解决一个具体问题       | Anthony Fu 在介绍里直接给去处，Maggie 的正文能展开定义，Steph 的主题页缩小阅读范围         | **常青笔记**。先看问题，原位展开这篇笔记的真实摘录，决定要不要跳到原文小节。项目页说明两篇文章与 Personal Blog 的实际联系。       | 点问题、读摘录、跳原文。退回时保留展开项。       |
| 我想知道作者具体做出了什么 | Josh 的输入、结果与实现文章相连，Emil 把可试的小样放在说明旁，Rauno 提前区分试原型与读实现 | **工程实验簿**。把此站中文阅读时长估算做成一个小实验，输入文本会改变字词统计和分钟数。想了解规则时进入 Personal Blog 的实现说明。 | 点预设或改文字，观察两类计数和估时，再去读实现。 |

**内容边界。** 两个方向使用同一项目与两篇完整正文。笔记摘录应来自文章本身，不能凭空设置「热门」或「成熟」状态。阅读时间沿用代码里的计数与取整规则；它是文本估算，不能代表某位读者的真实用时。中文、混排和短段落要显示原始计数，因为很短的文字变了几个字，整分钟结果可能仍是 1。站内输入、问题编排、导航反馈和视觉配色均为本次原创。[字词计数实现](../../src/lib/markdown/analyze.ts) · [项目记录](../../content/projects/zh-CN/personal-blog.md)

**选择标准。** 都用同一个项目和同一篇长文试一次。第一套看封面进出能否认出同一个作品；常青笔记看能否从一个问题抵达准确小节而不重找；工程实验簿看能否通过输入和输出说清一项功能。三个方向解决不同的访客任务，原站的用户规模、流量和商业成绩没有纳入判断。
